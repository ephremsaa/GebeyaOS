# GebeyaOS: Failure Scenarios & Self-Healing Matrix

In an Ethiopian supermarket retail environment, infrastructural instability (load shedding power cuts, dead CMOS batteries, intermittent fiber cuts, equipment failures) is a standard operating condition, not an anomaly. The following table specifies the exact technical safeguards, mitigation workflows, and data integrity guarantees for each failure scenario.

| Failure Event | Trigger & Immediate Impact | Technical Safeguards & Self-Healing Mechanism | Data Integrity Guarantee | Operator Recovery Procedure |
| :--- | :--- | :--- | :--- | :--- |
| **1. Sudden Power Loss Mid-Sale** | Sudden blackout or UPS battery depletion while cashier tenders payment or prints receipt. | 1. Line-interactive UPS provides ~15-30 mins battery runtime.<br/>2. If instant shutdown occurs, PostgreSQL WAL (Write-Ahead Logging) with `fsync=on` ensures ACID durability.<br/>3. Uncommitted transaction buffer pages are automatically rolled back during postgres startup WAL replay.<br/>4. Committed sales are durable on disk. | **Zero orphaned records; Zero corrupt DB pages.** Uncommitted sales are cleanly discarded; committed sales are permanently preserved. | On server reboot, PostgreSQL restarts automatically via Docker `restart: unless-stopped`. POS terminal re-authenticates and checks if last sale was committed; if not, cashier re-scans basket. |
| **2. Primary Branch Server SSD / DB Corruption** | Physical storage disk wear, filesystem corruption, or OS crash on the branch server PC. | 1. Automated nightly backups (`scripts/backup.sh`) compressed with gzip and stored locally on secondary drive/USB.<br/>2. Optional Warm Standby PC continuously synced or receiving backups.<br/>3. Standardized Docker Compose stack allows instant clean recreation. | Maximum potential data loss is limited to un-backed-up transactions or zero data loss if warm replica is active. | **Procedure A (Standby Failover):** Run `./scripts/failover.sh` on the warm standby PC. Standby assumes master role in < 2 mins.<br/>**Procedure B (Clean Restore):** On replaced PC, run `./scripts/restore.sh /backups/latest.sql.gz`. |
| **3. Internet Down for 7+ Days** | Fiber cut or Ethio Telecom / Safaricom outage leaves branch completely isolated from Central HQ for a week or more. | 1. **Local-Server-First Architecture:** POS lanes, inventory receiving, physical counts, shift reconciliation, and reports run 100% against the local branch server.<br/>2. Local server accumulates append-only events in `sync_outbox`.<br/>3. Monotonic `BIGSERIAL sequence_no` prevents sequence collisions. | **Zero interruption to sales; Zero data loss.** Local store remains fully functional indefinitely. | Cashier verifies digital Telebirr/CBE Birr payments via customer's SMS transaction reference. When internet is restored, sync worker automatically drains backlog in chunked batches. |
| **4. Two Terminals Scan Last Physical Unit** | Exactly 1 unit remains in stock; Cashier A and Cashier B scan and tender at the exact same millisecond. | 1. Checkout transaction acquires a row-level lock (`SELECT ... FOR UPDATE`) on candidate batches during FEFO allocation.<br/>2. The first terminal to commit successfully decrements the batch quantity.<br/>3. The second terminal receives an `InsufficientStockException` if `ALLOW_NEGATIVE_STOCK: false`.<br/>4. If branch policy permits negative stock (`ALLOW_NEGATIVE_STOCK: true`), the deficit is posted to the latest batch with an audit warning. | **No phantom stock.** Batch inventory balances and ledger movements accurately reflect physical allocations without race conditions. | If negative stock is disabled, Terminal B alerts cashier: "Insufficient stock. Item out of stock or requires manager override." Cashier removes item or supervisor enters override PIN. |
| **5. Duplicate Sync Packet Received at HQ** | Network drops after HQ successfully ingests a batch but before the branch receives the HTTP 200 ACK. Branch retries sending the same batch. | 1. Central `sync_inbox` enforces a unique constraint on `idempotency_key: {source_branch_id}_{entity_type}_{entity_id}_{sequence_no}`.<br/>2. When duplicate events are received, HQ detects the key exists and acknowledges the event IDs without re-applying the mutation.<br/>3. No duplicate rows inserted into sales or stock ledger. | **Strict Exactly-Once Ingestion Semantics.** Idempotent replay guarantees zero duplicated revenue, double-counted VAT, or doubled inventory decrements. | Fully autonomous; zero operator intervention required. Sync worker marks outbox events as `ACKNOWLEDGED`. |
| **6. Terminal Clock Wrong (Dead CMOS Battery)** | POS terminal CMOS battery dies or resets date to `2000-01-01` or drifts by hours. | 1. POS terminal synchronizes system time with the Branch Server via NTP / WebSocket handshake on login.<br/>2. Server validates transaction timestamp: if `abs(terminal_time - server_time) > 300s`, the server flags or overrides it with authoritative `server_timestamp = clock_timestamp()`.<br/>3. Monotonic ordering relies on UUIDv7 and sequence numbers, not terminal clocks. | **Financial audit integrity preserved.** Sales, shifts, and daily Z-reports reflect accurate authoritative store operating dates. | Branch server logs warning: "Terminal POS-01 clock drift detected (> 5 mins). Using server time." IT technician replaces CR2032 CMOS battery on terminal motherboard. |
